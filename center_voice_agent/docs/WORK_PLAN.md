# План работ: обёртка агента (LangChain) для голосового ИИ-наставника

Документ фиксирует **расширенное ТЗ** (этапы 1–3, 5, 7–8 + MCP + голосовой цикл) и порядок внедрения в репозитории `center_voice_agent/`. Профиль ребёнка **не** делаем как продуктовый UI — только **схема в БД** и доступ агента через обёртку.

---

## Принципы архитектуры

| Принцип | Реализация |
|--------|------------|
| Редактируемость без кода | Режимы и сценарии — **YAML/JSON в `config/`**; промпты — шаблоны в файлах или в БД (версия на выбор команды). |
| Точка входа (шлюз) | Один модуль **`agent_gateway`** (Runnable / граф): на входе состояние сессии, на выходе ответ + метаданные для TTS/логов. Всё остальное подключается снаружи. |
| Модель дообученная | Абстракция **`LLMProvider`**: endpoint, ключи, параметры из env/админки; LangChain `ChatOpenAI`-совместимый или кастомный `BaseChatModel`. |
| Голос | Вне агента: ASR → текст → **gateway** → текст → TTS. Агент остаётся текстовым; контракт полей под TTS (например `reply_spoken`) в ответе. |
| Логирование с первого дня | Структурированные логи + **correlation_id**; опционально LangSmith / OTEL позже. |
| БД | PostgreSQL (рекомендация) или SQLite на этапе разработки; долгосрочная память и «оболочка» профиля — в таблицах ниже по схеме. |

---

## Этап 1. Два типа контекста

### 1.1 Краткосрочная память

- Хранить **последние 15 реплик** (user/assistant), кольцевой буфер в памяти процесса или Redis при горизонтальном масштабе.
- Формат для LangChain: список `BaseMessage`, обрезка перед вызовом LLM.
- **Задачи:** модуль `context/short_term.py`, юнит-тест на лимит 15, сериализация для восстановления сессии (опционально таблица `session_messages` если нужен перезапуск сервера).

### 1.2 Долгосрочная память

- Содержимое: **имена, увлечения, предпочтения, прогресс по сценариям, заметки педагога** (что согласует юрист).
- Источник истины — **БД**; агент читает через инструмент `memory_search` / `memory_get_facts`, пишет через `memory_upsert` с политикой полей.
- **Задачи:** SQL-схема (`db/migrations/`), репозиторий `memory/repository.py`, маскирование ПДн в логах.

**Критерий приёмки:** в одном запросе к gateway в промпт попадают и 15 реплик, и краткая выборка из долгой памяти (через tool или prefetch).

## Этап 2. Режимы (динамические, расширяемые)

Реализовано в репозитории: см. **[MODES.md](MODES.md)** — YAML-режимы, `SessionCoordinator`, словарь команд, возрастные блоки, `ModeRegistry.reload_all()`, лог `modes_resolve`.

### 2.1 Точка входа «шлюз»

- Публичный API: `run_turn(state, user_text) -> AgentTurnResult`.
- Внутри: загрузка конфигурации режима из **файла или БД**, сборка промпта, выбор **набора инструментов** для режима, вызов LLM (LangChain `create_tool_calling_agent` или LCEL + `bind_tools`).

### 2.2 Конфиг режима (редактирует другой человек)

Поля минимум:

- `id`, `display_name`
- `system_prompt_path` или inline `system_prompt`
- `llm_params` (temperature, max_tokens, …)
- `tool_ids`: список включённых инструментов
- `allowed_transitions` (какие режимы доступны из UI/голоса) — опционально

**Задачи:** `modes/registry.py` — загрузка каталога `config/modes/*.yaml`, валидация Pydantic, горячая перезагрузка по сигналу или версии конфига.

**Критерий приёмки:** добавление нового файла режима **без изменения Python-кода** (кроме регистрации нового tool при появлении нового инструмента).

## Этап 3. Сценарии как граф

Реализовано в репозитории (файлы + сессия + БД + LangGraph): см. **[SCENARIOS.md](SCENARIOS.md)** — YAML-узлы, переходы, `on_interrupt`, `scenario_publish`, `SCENARIOS_SOURCE`, **`SessionCoordinator`**, LangGraph-цикл tools в шлюзе (`USE_LANGGRAPH`). Узел **`advance_scenario`** по-прежнему в шлюзе после ответа LLM.

### 3.1 Модель

- Граф: узлы = **этапы**, рёбра = **условия** (ответ ребёнка, команда, таймер, счётчик ошибок).
- Хранение: **YAML/JSON** в `config/scenarios/` + версия в БД (`scenario_definitions`).

### 3.2 Движок

- Интерпретатор графа: текущий `node_id`, переход по событию; состояние сценария в `state["scenario"]`.
- Интеграция с LangChain: **LangGraph** (рекомендуется) — узлы `load_context`, `llm`, `tool`, `advance_scenario`.

### 3.3 Переключение этапов + голос

- Внешний цикл: listen → ASR → **gateway** (режим + сценарий + память) → TTS.
- Голосовые команды смены режима/сброса сценария — таблица синонимов в конфиге.

**Критерий приёмки:** сценарий из файла проходит 3+ узла; прерывание вопросом и возврат к узлу (политика в конфиге сценария).

## Этап 4. Инструменты (MCP + LangChain)

### 4.1 Набор инструментов v1

| Tool | Назначение | Редактируемость |
|------|------------|-----------------|
| `web_search` | Поиск в сети (обёртка над вашим API) | Параметры и провайдер в конфиге |
| `memory_search` | Запрос к долгосрочной памяти | SQL/лимиты в конфиге |
| `memory_upsert` | Запись фактов (с whitelist полей) | Схема БД + валидация |
| (позже) `rag_search` | Методички центра | Индекс + метаданные |

### 4.2 MCP

- Каждый инструмент — **одна чёткая JSON-schema** (совместимость с MCP).
- Реализация: либо **stdio MCP-сервер** вызывает те же функции, что и LangChain tools, либо наоборот — thin-wrapper вокруг MCP-клиента внутри агента. Цель: **одна бизнес-логика**, два транспорта.

**Задачи:** вынести реализацию в `tools/impl/`, LangChain — `tools/langchain_exports.py`, MCP — `mcp/server.py` (итерация 2).

## Этап 5. Логирование (обязательно сразу)

- Уровни: DEBUG для разработки, INFO для прод.
- Обязательные поля: `timestamp`, `level`, `correlation_id`, `session_id`, `mode_id`, `scenario_id`, `node_id`, `latency_ms`, `tool_calls` (имена без чувствительного текста по умолчанию).
- Отдельный канал **security_incident** при срабатывании модерации (позже).

## Этап 8. «Очень хорошее» логирование (уровень A)

- Структурированный JSON в stdout + ротация файлов (`logs/agent.log`).
- **Трасса одного turn:** этапы `gateway_in` → `modes_resolve` → `scenario_step` → `tools` → `llm` → `gateway_out`.
- Метрики: длительность LLM, retriever, БД; счётчики ошибок.
- Подготовка к LangSmith: `LANGCHAIN_TRACING_V2` и теги (без сырых ПДн в тегах).

## Порядок работ по спринтам (для постепенной загрузки в git)

1. **S0 — каркас репо** (текущий коммит): структура, зависимости, план, схема БД, примеры конфигов, заглушки gateway и логов.
2. **S1** — краткая/долгая память + репозиторий SQLite/PG + тесты буфера 15.
3. **S2** — registry режимов из YAML + разные toolsets + промпты из файлов.
4. **S3** — движок графа сценария + интеграция в gateway (LangGraph).
5. **S4** — реальные tool-вызовы (поиск, память), политика ошибок и пустых результатов.
6. **S5** — MCP-обёртка поверх тех же impl.
7. **S6** — голосовой демо-раннер (reuse ASR/TTS из другого репо или минимальный stdin/stdout).
8. **S7** — модерация, инциденты, нагрузочный скелет.

Каждый спринт — **отдельный коммит/тег** (`s0-scaffold`, `s1-memory`, …) для отката.

## Риски

- ПДн в логах — по умолчанию **не** логировать сырой текст ребёнка; только хэш/длину/флаг.
- Дообученная модель может не поддерживать tool-calling — иметь запасной путь (принудительный JSON в ответе + парсер).
- MCP на Windows — тестировать stdio в CI и локально.
